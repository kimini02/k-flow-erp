# 프론트엔드 포트폴리오 설명 초안

기준: 2026-09-29. 아래는 실제 구현 범위에 맞춘 설명 초안이다. 본인이 직접 설명하고 재현할 수 있는 내용과 역할만 최종 포트폴리오에 사용한다.

## 1. 프로젝트 소개 문장

> K-Flow ERP는 한국 제조·유통 기업의 전자결재와 구매·재고·판매·생산·회계·인사 업무를 시연하는 React/TypeScript 프론트엔드입니다. 업무별 목록과 문서 상세를 공통 UI로 구성하고, 구매요청에서 결재·발주·입고로 이어지는 상태 전이와 문서 연결을 브라우저 Mock로 구현했습니다. Spring Boot 연결을 위한 API adapter와 계약을 마련했으며 실제 인증·DB·동시성 처리는 다음 개발 단계입니다.

## 2. 문제와 해결 접근

ERP에는 비슷한 목록·폼이 많지만 문서의 상태와 후속 업무가 다르다. 메뉴별로 화면을 각각 만들면 검색·오류 처리·입력 UI가 쉽게 달라지고 같은 수정이 반복된다. 이를 줄이기 위해 화면의 공통 구조와 업무별 설정을 분리했다.

`Resource`에 컬럼, 필드, 상태, 액션을 정의하고 공통 `DocumentListPage`, `DocumentForm`, `DocumentDetails`에서 재사용했다. 재무제표처럼 구조가 다른 화면은 전용 컴포넌트로 분리했다. 이 구조로 54개 경로를 구성했으며 54개의 독립 페이지를 작성한 것은 아니다.

문서가 단순히 목록에 존재하는 것보다 왜 생성됐고 다음 단계가 무엇인지 보여주는 데 초점을 맞췄다. 원천/후속 문서 링크, 결재 타임라인, 상태별 액션, 감사 이력으로 업무 흐름을 표현했다.

## 3. 설명할 설계 결정

| 결정 | 구현 근거 | 이점과 한계 |
| --- | --- | --- |
| 설정 기반 공통 UI | Resource/Module, feature config, catalog | 반복 UI 통일. 복잡한 기능은 공통 컴포넌트 분기가 늘 수 있음 |
| 목록 위 상세 Drawer | DocumentDetails, `?doc=` | 목록 맥락과 상세 링크 유지. 모든 필터가 URL에 저장되지는 않음 |
| 비동기 데이터 계층 분리 | ErpClient, Query hooks | Mock/REST 교체 지점 확보. DTO·권한·집계 변경 시 추가 수정 필요 |
| 업무 명령과 일반 저장 구분 | save/transition/approve | 승인·입고 같은 업무 행동을 별도 처리. 현재 명령 이름은 한글 문자열 |
| 관련 캐시 재조회 | `invalidateQueries(['erp'])` | 연결 문서와 KPI 갱신 단순화. 운영에서는 범위 최적화 필요 |
| Mock 복사본 commit | store, effects | 중간 실패 시 원본 보존 시연. 서버 트랜잭션 대체 불가 |
| AI 쓰기 확인 단계 | AssistantDrawer | 초안 제안과 실제 생성 구분. LLM은 아직 없음 |

실제 시간 절약률, 성능 향상률, 사용자 수는 측정하지 않았으므로 임의 수치를 성과로 쓰지 않는다.

## 4. 아키텍처 슬라이드에 담을 내용

현재 아키텍처 그림은 [FRONTEND-ARCHITECTURE.md](FRONTEND-ARCHITECTURE.md)의 Mermaid를 사용한다. 브라우저 내부의 UI → Query → adapter → Mock store → localStorage가 현재 구현이다.

향후 아키텍처는 [BACKEND-HANDOFF.md](BACKEND-HANDOFF.md)의 그림으로 분리한다. Spring Boot, DB, 인증, 트랜잭션을 현재 구현 그림의 완료된 구성 요소로 넣지 않는다. 백엔드를 실제 연결한 뒤 문서 날짜와 검증 근거를 갱신한다.

## 5. 화면과 시연 순서

1. [대시보드](screenshots/dashboard.png): 메뉴 구조, 업무 요약, 이동 경로를 보여준다.
2. 구매요청 신규 작성: 품목행, 금액, 필수 입력을 설명한다.
3. [결재 상세](screenshots/approval.png): 데모 사용자 전환 후 현재 결재자만 처리되는 흐름을 설명한다.
4. 승인된 구매요청에서 발주 생성: 관련 문서를 따라가며 원천과 후속 관계를 보여준다.
5. [구매 상세](screenshots/purchase-detail.png): 상태별 액션과 이력/관련 문서를 설명한다.
6. [보고서](screenshots/reporting.png): 문서 집계 기준과 초록 계열 표시를 보여준다.
7. [Assistant](screenshots/assistant.png): Mock 초안 제안, 취소, 확인 후 생성의 차이를 보여준다.

데모 문서의 날짜는 2026년 9월을 기준으로 한다. 초기 샘플의 완성 문서를 보는 것보다 새 문서를 만들어 순서대로 처리하면 흐름이 명확하다. 데이터 초기화는 기존 시연 데이터가 삭제되므로 필요할 때만 수행한다.

## 6. 검증 설명 문장

> Mock 업무 로직을 대상으로 구매부터 지급·전표까지의 연결, 결재 권한, 금액 배분, 전표 균형, 재고 이동과 실패 시 원본 보존 등을 검사했습니다. 초기 검증에서 Vitest 업무 테스트 10개와 Playwright 브라우저 시나리오 8개가 통과했습니다. 이 결과는 프론트엔드와 Mock 범위이며 실제 Spring DB 트랜잭션이나 다중 사용자 환경 검증은 별도로 진행할 예정입니다.

정확한 실행 이력은 [VALIDATION.md](VALIDATION.md)를 참조한다. 이후 색상 변경의 검증과 초기 전체 테스트 실행은 구분해서 기록한다.

## 7. 면접 질문에 답하는 예

**왜 먼저 프론트엔드를 만들었나요?**

화면에서 필요한 필드와 사용자가 실행하는 명령을 먼저 구체화하기 위해서입니다. 예를 들어 구매요청 저장과 결재 상신, 발주 생성은 다른 행동입니다. 시연 흐름을 통해 API를 단순 CRUD로만 나누면 부족한 부분을 확인했고, 이를 백엔드 도메인 설계의 입력으로 사용하려고 합니다.

**TanStack Query는 어떤 역할인가요?**

폼 입력이나 Modal 상태는 React state로 관리하고, 목록·상세처럼 비동기로 읽는 데이터는 Query로 관리했습니다. 저장 성공 후 연결된 문서와 KPI를 다시 조회합니다. 현재는 넓게 invalidate하지만 서버 연결 후 기능별로 범위를 줄일 수 있습니다.

**백엔드는 환경변수만 바꾸면 끝인가요?**

아닙니다. adapter 선택 지점은 있지만 실제 인증 사용자, 업무별 DTO, 명령 코드, 집계 API, 오류 응답을 연결해야 합니다. 공통 폼과 상세가 Mock store의 검증 함수를 직접 참조하는 부분도 정리 대상입니다.

**권한이나 트랜잭션을 구현한 건가요?**

현재 결재 순서와 일부 상태 규칙은 브라우저에서 시연합니다. 복사본을 성공 시에만 저장해 실패한 변경이 원본에 남지 않도록 했지만, 이는 서버 보안이나 DB 트랜잭션을 구현한 것과 다릅니다. 실제 사용자 권한, 동시 승인, 재고 변경의 원자성은 Spring에서 처리해야 합니다.

**AI 기능은 어디까지인가요?**

정해진 질문을 분류하는 Mock와 근거 링크, 초안 확인 UI까지입니다. 실제 모델이나 RAG는 아직 없으며, 확인 버튼을 누른 경우에만 구매요청을 저장합니다.

## 8. 제작 방식과 출처

이 프론트엔드는 사용자의 요구사항과 디자인 피드백을 바탕으로 Codex의 코드 작성·수정·검증 지원을 받아 제작했다. 실제 본인의 기여 범위에 맞춰 기획, 요구사항 검토, 디자인 피드백, 코드 이해·수정, 백엔드 설계/개발 역할을 구분해 적는다. AI가 작성한 코드를 모두 직접 작성했다고 표현하지 않는다.

기존 ERP 저장소를 참고한 구조/UX 분석은 [REFERENCE-ANALYSIS.md](REFERENCE-ANALYSIS.md)에 기록했다. 원본 소스/자산을 그대로 복사한 프로젝트라는 설명도, 참고 없이 전부 독자적으로 고안했다는 설명도 현재 기록과 맞지 않는다.

## 9. 다음 단계에서 추가할 포트폴리오 근거

백엔드 구현 후 실제 ERD, 상태 전이표, OpenAPI 또는 API 문서, 인증/인가 흐름, 트랜잭션 경계, 동시성 테스트, 실행·배포 방법을 추가한다. 먼저 구매·결재·발주·입고의 한 흐름을 실제 DB까지 완성하고, 그 과정에서 해결한 문제와 테스트 결과를 남긴다.
