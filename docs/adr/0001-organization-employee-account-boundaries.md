## 1. 기록의 성격과 근거

이 ADR은 이미 사용자가 채택한 E-01/E-02 정책을 저장소의 결정 기록 형식으로 새로 정리한 초안이다. **과거 ADR 원본을 복원한 문서가 아니다.** 작성 근거는 사용자의 채택 지시와 최신 상세설계 1.1절의 ADOPTED 정책이다. 과거 ADR의 문구, 작성일, 승인 이력 또는 당시 대안 비교를 복원했다고 주장하지 않는다.

확인한 커밋에는 상세설계 파일이 있으며, 그 파일이 참조하는 이 ADR 경로는 없다. 같은 커밋의 ERD Overview는 E-01/E-02를 아직 OPEN / DRAFT로 표시한다. 이것은 문서 반영의 차이이며, 채택된 정책을 다시 OPEN으로 돌리는 근거가 아니다.

문서 상태 DRAFT와 정책 상태 CLOSED는 다른 뜻이다. 이 초안의 문구와 저장소 반영을 검토하되, 이미 채택된 정책을 재결정하지 않는다. 상세설계의 DESIGN v0.1 후보를 이 ADR의 채택 정책으로 승격하지 않는다.

## 2. 배경과 질문

단일 법인 한결 인더스트리의 복수 사업장 환경에서 조직 기준, 직원의 인사 이력, 로그인 계정, 시스템 역할을 구분해야 한다. 인사상 직원이 모두 시스템 계정을 가져야 하는 것은 아니며, 직급과 시스템 권한도 같은 개념이 아니다.

| 질문 | 원래 결정 대상 | 이 ADR의 처리 |
| --- | --- | --- |
| E-01 | 부서와 사업장의 관계, 직원의 주 소속·겸직·전보 이력, 직급 배정 | 아래 3.1절의 채택 정책으로 CLOSED |
| E-02 | Employee↔User 연결 수, 직원 미연결 사람 계정, UserRole 저장 표현 | 아래 3.2절의 채택 정책으로 CLOSED |

단일 법인·복수 Site/Warehouse 및 Department·Site·Warehouse의 구분은 기존 채택 범위다. 이 ADR에서 다법인, 창고 운영, 급여·근태·연차 또는 결재선 상세 범위를 추가하지 않는다.

## 3. 결정

### 3.1 E-01 조직과 직원 배치

| ID | 채택된 결정 | 의미 |
| --- | --- | --- |
| E01-1 | Department와 Site는 독립된 기준이다. | 부서가 하나의 사업장에 종속된다는 관계를 강제하지 않는다. Warehouse는 별도 개념이다. |
| E01-2 | Position은 회사 공통 인사 직급이다. | Department에 종속시키거나 시스템 Role과 동일시하지 않는다. |
| E01-3 | 재직 중 현재 주 Department·Site·Position은 각각 정확히 1개다. | 동시 겸직은 v1에서 지원하지 않는다. |
| E01-4 | 기간별 소속·사업장·직급 이력은 HR 소유 EmployeeAssignment에 보존한다. | Organization은 조직 기준을, HR은 직원의 인사 배치 이력을 소유한다. |

### 3.2 E-02 직원과 계정 및 역할

| ID | 채택된 결정 | 의미 |
| --- | --- | --- |
| E02-1 | Employee 한 명은 User를 0..1개 가진다. | 계정 없는 직원은 정상이며, 직원당 복수 계정은 v1 미지원이다. |
| E02-2 | v1의 사람 User는 Employee 정확히 1명과 연결한다. | 직원 미연결 사람 계정은 지원하지 않는다. |
| E02-3 | User↔Role은 N:M이고 UserRole을 명시적 연결 Entity/Table로 둔다. | 역할을 CSV 문자열로 저장하지 않는다. |
| E02-4 | 유효한 Allow 권한을 합집합으로 결합한다. 명시적 DENY 권한/Role은 v1 미지원이다. | 권한이 없어서 거부되는 것과 DENY 역할을 저장하는 것은 구분한다. 이 결정이 Data Scope의 결합 규칙까지 정한 것은 아니다. |
| E02-5 | 퇴사자의 Employee/User와 과거 거래·결재·감사 참조를 보존하고, 퇴사자는 로그인 비활성화한다. | 접근 종료와 이력 삭제를 같은 처리로 만들지 않는다. 상태명·세션 처리 기술은 별도 설계다. |
| E02-6 | User 전역 Data Scope를 두지 않으며, Scope는 업무/권한별로 달라질 수 있다. | 원칙만 채택한다. 구체 저장 구조와 Scope 표는 도메인별 후속 결정으로 남긴다. |

Position만으로 시스템 권한을 부여하지 않고, APPROVER Role만으로 실제 결재자를 결정하지 않는 기존 채택 경계를 유지한다. 실제 결재 담당자·대결·결재선은 Approval 후속 설계 대상이다.

### 3.3 소유 책임

| 영역 | 책임 |
| --- | --- |
| Organization | Company, Site, Department, Position의 기준 정의 |
| HR Core | Employee의 인사 원본과 EmployeeAssignment의 기간별 배치 이력 |
| IAM | User의 계정 원본, Role, UserRole 및 인증·시스템 접근 권한 |

Employee의 재직 상태와 User의 계정 상태를 하나의 상태로 합치지 않는다. 직원의 인사 이력과 계정의 역할 변경은 각각의 소유 책임에서 다룬다.

## 4. 채택 범위 밖의 상세설계

다음은 상세설계 v0.1의 후보 또는 별도 OPEN 항목이다. 이 ADR의 결정으로 확정하지 않는다.

| 후속 항목 | 유지할 상태 |
| --- | --- |
| 상태 enum, 최초 계정 상태, Role 비활성화·재활성화·일괄 철회 lifecycle | DESIGN v0.1 / OHI-05·06 후속 |
| Assignment를 현재 소속의 단일 저장 원본으로 삼는 구체 모델, [from, to) 기간·시간대·당일 변경 제한 | DESIGN v0.1 / OHI-01 후속 |
| UUID·테이블명·컬럼명·코드 정규화·업무번호 변경 | DESIGN v0.1 / OHI-08 후속 |
| FK·복합 FK·EXCLUDE·partial UNIQUE·version 및 Lock 강도·순서·격리 | DESIGN v0.1 / OHI-09 기술 검증 |
| Published Port의 이름·입출력, Actor의 위치, REST URL·HTTP 오류·재시도 계약 | DESIGN v0.1 / 관련 후속 설계 |
| 퇴사 후 기존 세션·토큰의 접근 차단 구현, 매 요청 조회·캐시 | DESIGN v0.1 / OHI-06 후속 |
| 조직 계층·부서장·직책·재입사·퇴사 취소·초기 이관 | OHI-01·04·07 OPEN |
| 사용 중 조직 기준의 비활성화에서 재배치를 강제하는지 | OHI-03 OPEN |
| 필수 감사의 저장 경계·보존·실패 시 업무 성공 여부 | DR-25 / E-14 OPEN |

### 4.1 사용자 명시 OPEN

**OHI-00 — Data Scope:** 구체 저장 구조, 지원 Scope, Scope 표, 복수 Scope 결합, 민감 필드 공개 범위는 도메인별 후속 결정이다. 이 ADR에는 Scope 표나 Permission/Scope 연결 테이블을 정의하지 않는다.

**OHI-02 — 휴직 로그인:** 휴직 시 신규 로그인, 기존 세션 접근, 계정 상태와의 조합, 복귀 영향은 OPEN이다. 휴직을 자동 로그인 허용 또는 자동 차단으로 확정하지 않는다.

E-01/E-02가 CLOSED라는 사실만으로 이 OPEN 항목의 정책이나 구현 준비가 완료됐다고 표시하지 않는다.

## 5. 선택 이유와 영향

아래 설명은 채택 정책의 의미를 정리한 것이다. 당시 논의 과정이나 선택 이유의 원문을 복원한 기록은 아니다.

- 부서와 사업장을 독립시키면 같은 부서의 직원이 서로 다른 사업장에서 근무하는 상황을 표현할 수 있다.
- Employee와 User를 분리하면 계정 없는 직원도 인사 원본으로 유지하고, 퇴사 후 접근을 종료하면서 과거 신원 참조를 보존할 수 있다.
- Position과 Role을 분리하면 인사상 직급 변경을 곧바로 권한 상승 또는 실제 결재자 변경으로 처리하지 않는다.
- EmployeeAssignment와 명시적 UserRole은 인사 배치와 계정 역할을 각각 식별 가능한 모델로 다루게 한다. 구체 기간·부여/철회 저장 규칙은 상세설계 검토가 필요하다.
- v1에서는 단일 주 소속과 직원당 최대 1계정을 전제로 한다. 겸직·복수 계정·직원 미연결 사람 계정을 추가하려면 별도 정책 결정이 필요하다.
- Allow 합집합의 채택은 모든 업무 데이터를 볼 수 있다는 뜻이 아니다. 각 도메인은 행위 권한과 대상 데이터 접근 조건을 후속 설계해야 한다.

## 6. 정책 적합성 확인 기준

아래는 구현 이후 확인할 정책 조건이며, 테스트 실행 결과가 아니다.

| 결정 | 확인할 조건 |
| --- | --- |
| E01-1·2 | 같은 부서의 직원을 서로 다른 Site에 배정할 수 있고 Position이 부서에 종속되지 않는다. |
| E01-3·4 | 재직 중 유효한 주 소속이 정확히 1개이며, 전보 후 이전 배치 이력이 남는다. |
| E02-1·2 | 직원만 존재할 수 있고, 한 직원에게 두 사람 계정이 만들어지거나 사람 계정의 직원 연결이 누락되지 않는다. |
| E02-3 | 한 User가 복수 Role을 가질 수 있고 UserRole이 명시적으로 식별된다. |
| E02-4 | 유효한 Allow 권한을 합집합으로 평가하되 명시적 DENY 모델을 추가하지 않는다. |
| E02-5 | 퇴사 후 로그인 접근을 종료하면서 Employee/User와 과거 참조를 보존한다. |
| E02-6 | User 전역 Scope를 저장하거나 전체 업무의 데이터 범위를 User 하나의 값으로 정하지 않는다. |
| 사용자 명시 OPEN | 휴직 로그인 결과와 도메인별 Scope 행렬을 미결 상태에서 임의 기대값으로 고정하지 않는다. |

구체 DB·경계·동시성 테스트 후보는 [상세설계 9절](../specs/organization-hr-iam-detailed-design-v0.1.md#9-테스트해야-할-불변조건)을 따른다.

## 7. 후속 문서 반영

저장소 반영 시 이 ADR을 위 경로에 신규 추가한다. ERD Overview의 E-01/E-02 등록부와 관련 관계 설명은 채택 정책에 맞게 동기화하고, Project Index에 상세설계·ADR·계획을 연결한다. E-03~E-15 또는 관련 DR의 OPEN 상태를 함께 닫지 않는다.

이 ADR 초안 작성은 Astra 구현 착수 지시가 아니다. 구현 순서·선행 결정·검증 종료점은 별도 [Implementation Plan](../plans/organization-hr-iam-implementation-plan-v0.1.md)에서 다룬다.
