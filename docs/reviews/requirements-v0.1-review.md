프로젝트의 기존 REQUIREMENTS v0.1과
docs/reviews/requirements-v0.1-review.md를 먼저 읽어라.

이번 작업의 목적은 Backend 구현이 아니다.

기존 REQUIREMENTS v0.1은
"현재 Frontend/Mock 동작을 분석한 기록"으로 보존하고,
리뷰 내용을 반영하여
"실제로 Backend에서 구현할 목표 업무 요구사항 v0.2"를 작성한다.

중요한 원칙:

1. 기존 v0.1을 삭제하거나 덮어쓰지 않는다.
2. review 문서의 내용을 무조건 정답으로 복사하지 않는다.
3. 반드시 다음 세 종류를 구분한다.

- 현재 Frontend에서 확인된 사실
- 국내 ERP/회계/법규 자료에서 확인된 사실
- 한결 인더스트리를 위해 우리가 선택하는 Project Policy

특히 Project Policy를
"한국 기업은 원래 이렇게 한다"
라고 표현하지 않는다.

이번에 우선 검토할 핵심 정책은 다음이다.

1. 회사/품목 역할

- 자체 생산품
- 구매 원재료/반제품
- 재판매 상품
- 내부 사용 품목
  을 구분한다.

2. 구매/입고

- 입고 문서 생성과 실제 입고 확정을 구분한다.
- 부분입고는 확정된 누적 수량을 기준으로 판단한다.
- 하나의 PO에 여러 Goods Receipt를 허용한다.
- 초과입고/잔량취소 정책을 정의한다.

3. 판매/출고

- 출고 문서 생성과 실제 출고 확정을 구분한다.
- 부분출고 역시 누적 확정 수량을 기준으로 한다.

4. 제조

- 계획수량과 실제 생산실적을 분리한다.
- 양품/불량/부분실적/추가투입/잔여 WIP 중
  이번 프로젝트가 어디까지 지원할지 정의한다.

5. 기준정보

- 거래처를 문자열이 아닌 Master Data로 관리한다.
- Item/Employee/Partner/Account 참조 방식도 안정적인 ID 기반으로 검토한다.

6. 수량/단위

- EA뿐 아니라 KG/BOM 비율 등에 필요한 Decimal Quantity를 검토한다.
- 금액 정밀도와 수량 정밀도를 분리한다.

7. 날짜

- 작성일, 요청일, 입고일, 증빙일, 전기일, 지급기한 등
  업무 의미가 다른 날짜를 하나의 date/dueDate로 뭉뚱그리지 않는다.

8. 회계/세금

- 공급가액 / 부가세 / 공급대가를 구분한다.
- AP/AR에 어떤 금액이 반영되는지 정의한다.
- 입고와 매입 사이 회계처리 방식은
  GR/IR 포함 여러 후보를 비교한 뒤 결정한다.
- 매출원가 인식 시점을 별도 설계 대상으로 둔다.

9. 전자세금계산서

- 내부 매출문서와 전자세금계산서를 동일 개념으로 취급하지 않는다.
- 외부 발급 시스템 연동 범위를 명시한다.

10. 반품

- 재고 복귀뿐 아니라
  AR 감소 / 기수금 / 환불·상계 / 회계 정정까지
  어떤 범위를 지원할지 정의한다.

11. 전자결재

- 고정 3단 결재를 한국 기업의 일반 규칙처럼 표현하지 않는다.
- 문서종류/부서/금액 등에 따른 회사 정책으로 정의한다.
- Approval 완료와 ERP 후속 업무 완료를 구분한다.

12. HR

- 연차를 단순 15-days로 계산하지 않는다.
- 법정 발생 계산을 직접 구현할지,
  확정된 개인별 부여량을 입력받아 잔액만 관리할지 범위를 결정한다.
- 급여도 부서 합계 관리인지 직원별 Payroll인지 명확하게 정의한다.

13. 품질/추적

- 전자부품 제조라는 회사 설정상
  검사대기/사용가능/불량 재고 및 LOT/Serial 추적을
  이번 범위에 포함할지 검토한다.

14. 창고이동

- 즉시 장부대체인지
  출발→운송중→도착 모델인지 정책을 정한다.

REQUIREMENTS v0.2의 각 요구사항은 가능하면 다음 형식을 사용한다.

[ID]
[업무 영역]
[요구사항]
[Business Rule]
[Acceptance Criteria]
[미정 정책 여부]

예:

PUR-02
업무: 부분입고

요구사항:
입고 문서 초안 생성만으로 발주 입고량과 재고를 변경하지 않는다.

Business Rule:
Goods Receipt가 확정될 때
PO Line의 누적 확정 입고수량을 갱신한다.

Acceptance Criteria:

- PO 100개 / 입고 초안 30개 → 누적입고 0
- 해당 입고 확정 → 누적입고 30, PARTIALLY_RECEIVED
- 추가 70 확정 → 누적입고 100, RECEIVED
- 누적 100 이후 추가 입고 → 정책에 따라 거부 또는 별도 허용 절차

미정:
초과입고 허용 정책

중요:
아직 ERD, API, Entity, Repository, Service,
Controller, Migration을 구현하지 않는다.

현재 단계에서는
"업무 요구사항을 현실적인 ERP Flow로 정제하는 것"
까지만 한다.

확신할 수 없는 정책은 임의로 정하지 말고
[DECISION REQUIRED]로 표시한다.

작업 완료 후 다음만 보고한다.

1. v0.1에서 변경된 핵심 요구사항
2. 새롭게 추가한 요구사항
3. 삭제/수정이 필요한 현재 Frontend 동작
4. DECISION REQUIRED 목록
5. Backend 설계 전에 반드시 확정해야 하는 정책

그 후 멈춰라.
