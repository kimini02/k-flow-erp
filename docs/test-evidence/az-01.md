## 구현 계약과 Trade-off

경로 기준: `backend/src/main/java/com/kflow/erp/iam/`.

| 구성 | 실제 역할 |
|---|---|
| `api/Action` | 정확한 action 식별자 2개. unknown/null/공백·대소문자 변형은 거부 |
| `api/ActionAuthorization` | `requireCurrent(action)`은 Role 적격성만 검사. void 반환으로 재사용 가능한 permit을 주지 않음 |
| `application/authorization/ActionAuthorizationService` | 매 호출 `PrincipalAccessQueries.requireCurrent()`로 현재 요청·thread의 AN-03 신원 획득, 기존 `iamClock`으로 expiry/Company/readiness 검사. 임의 주체 인자 없음 |
| `application/authorization/ActionPolicy` | package-private 순수 함수. 한 행 안에서 Role+action+target을 모두 평가. Site/ReaderGrant 두 대상만 존재 |
| `application/authorization/PolicyBindings` | 회사별 canonical code 양방향 조회→실제 Stable UUID. immutable identity binding; ACTIVE·grant cache가 아님 |
| `application/authorization/ActionPolicyConfiguration` | 프로세스 시작 시 바인딩 1회. 미설정·실패는 unready이며 기존 인증 서버를 임의 개방하거나 중단하지 않음 |

| action | 정확한 Role code | 동일 행 대상 조건 | 이번 보장 |
|---|---|---|---|
| `organization.site.read` | `ORG_SITE_READER` 또는 `IAM_ACCESS_OPERATOR` | owner가 제공한 Site Company = 현재 신원 Company | `requireSiteRead` 정책 평가. 실제 Site HTTP API는 AZ-02 NOT_RUN |
| `iam.user-role.grant-site-reader` | `IAM_ACCESS_OPERATOR`만 | 같은 Company, 다른 User 및 다른 Employee, 정확히 reader 바인딩 ID | `requireReaderGrantTarget` 정책 적격성만. 재직/최종 Guard/MFA/Audit/실제 grant commit은 AZ-03 이후 |

`requireCurrent` 성공만으로 대상 read/write를 수행하면 안 된다. 대상 사실은 소유 Module에서 얻어 해당 target 검사와 결합해야 한다. 순수 함수의 입력은 신뢰 경계가 아니며 Published API는 RequestPrincipal/임의 actor/user 권한 조회를 받지 않는다. target User ID는 임의 사용자의 권한 조회 인자가 아니라 검증할 대상 사실이다. ActionAuthorization은 현재 요청 내 검사를 수행할 뿐 실제 관리자 명령을 제공하지 않는다.

### 바인딩과 readiness

- release ID: **`kflow-az-01-v1`** (코드 고정). 회사 ID는 운영 UUID 하드코딩 없이 승인된 배포 입력 `kflow.authorization.company-id`로 받는다.
- `kflow.authorization.expected-policy-release`는 승인된 배포 manifest의 기대값이며 위 release와 정확히 일치해야 한다. 두 설정 모두 기본값이 비어 있어 **NOT_CONFIGURED/deny**다. 설정 자체가 운영 승인·신뢰 operator 준비를 대신하지 않는다.
- `RoleQueryService`가 기존 singleton Company를 확인한다. code→ID와 ID→code/Company를 모두 확인하고 누락/alias/회사·code·ID 불일치는 INVALID_BINDING, 조회 장애는 UNAVAILABLE로 고정한다. 자동 seed/activate/grant/retry/ADMIN fallback 없음.
- INACTIVE Role도 정체성 ID는 바인딩할 수 있다. 실제 현재 유효 Role은 **다음 요청 Q**의 ACTIVE·미철회 grant 집합만 사용한다. rename·상태·일반 version은 identity binding에 사용하지 않는다.
- immutable 바인딩이므로 Role 준비나 복원 뒤 재시작/재바인딩이 필요하다. 런타임 refresh·DB 정책·Role cache가 없다. 이것은 추가 조회를 없애는 대신 재배포/재시작을 요구하는 선택이다.
- **READY는 바인딩 준비만 의미한다.** 실제 Role activation·operator 준비, 운영 노드 전체 release 일치, AZ-02/03 기능 및 공개 Gate 완료를 의미하지 않는다.
- 서로 다른 기대 release는 로컬 gate에서 deny한다. 실제 두 배포 노드의 drift 자동 탐지/동기화 또는 운영 fleet 검증은 구현하지 않았으며 **운영 OPEN**이다. 테스트용 구성 불일치 결과를 실제 다중 노드 운영 검증으로 확대하지 않는다.

### 진입·의존 경계

Production에 Site/grant Controller·worker·scheduler를 추가하지 않았다. 기존 AN-03 Filter ordering, dispatcher 차단, 업무·관리 경로 default deny를 변경하지 않았다. `OrganizationReferenceQueries.findSite`는 내부 fact Port 그대로다. Organization/HR→IAM 역참조 없음. 14개 Module 유지.

`AuthorizationArchitectureTest`는 raw User/Role/UserRole writer의 현재 허용 호출자를 기존 Bootstrap으로 제한하고, 새 production findSite 반환 진입과 추가 Controller가 없음을 확인한다. AZ-02/03에서 실제 secured entry를 도입할 때만 이 inventory를 명시적으로 갱신해야 한다. 동일 JVM 악성 코드/특권 raw SQL까지 방어한다는 뜻은 아니다.

## 실제 실행과 개발 기록

- Java 21로 두 번의 초기 선별 verify는 성공했다. 첫 전체 verify에서는 Surefire 148 / Failsafe 880 실행 중 **Failures 1 / Errors 11 / Skipped 0**으로 실패했다. 새 `ActionAuthorizationService`가 웹 전용 `sessionClock`을 필수 의존하여, 비웹 SpringApplication으로 재시작하는 기존 Organization/Migration 시험에서 Bean 생성이 실패한 **실제 구현 결함**이다. missing-Company 오류를 검증하던 기존 assertion 1건도 이 선행 초기화 실패의 영향을 받았다. 모든 환경에 이미 존재하는 `iamClock`을 주입하도록 고쳤다. 기존 테스트·기대값·Migration은 수정하거나 무시하지 않았다. 실패 원문, 같은 실패 시험들의 선별 재실행, 최종 전체 실행을 각각 보존한다. 실제 Spring 서비스의 미설정 deny 시험도 추가했다.
- 수정 후 두 번째 전체 verify는 Surefire 148 / Failsafe 881, Failures 1 / Errors 0 / Skipped 0이었다. 기존 `AuthenticationLiveIT`에서 AZ-01이 포함되지 않은 pinned AN-02 실행 파일의 45초 readiness 대기 한도를 넘었다(`awaitReady`, 테스트 line 127). 이 실행의 child 상세 로그는 기존 cleanup으로 남지 않아 근본 원인은 확정하지 않는다. 이어진 단독 재실행은 AN-02 child 기동을 통과했지만 Chrome `first` 단계의 40초 deadline으로 실패했다(Surefire 40 / Failsafe 1, F1/E0/S0). 로컬 고부하와 Chrome 디스플레이 오류도 관찰했지만 인과관계는 확정하지 않는다. 테스트 코드·기대값·timeout을 바꾸지 않고 최종 전체 재검증을 수행했으며, 두 실패와 재실행 로그를 모두 개발 기록에 보존한다. AZ-01 정책 실패로 단정하거나 원인이 해결됐다고 과장하지 않는다.
- 추가로 executive 표시 Position을 가진 Role0 fixture를 최종 전체 verify에서 검증했다. 직급의 표시명은 권한 근거가 아니다.
- HTTP integration은 실제 Spring Session JDBC·로그인·PostgreSQL Q·SecurityFilterChain과 MockMvc를 사용한다. `AuthController.session`에 테스트 spy를 두어 Q 이후 보호 façade를 호출한다. **실제 AZ-02 Site Controller/관리 grant API가 아니다.** 실제 서버·브라우저·두 JVM은 기존 AN-03 회귀가 실행하며 AZ 다중 노드 정책 drift 시험으로 집계하지 않는다.
- Fixture Employee는 2026-10-01 실제 등록 commit, writer/Q Clock은 별도 2026-10-11이다. FK/CHECK를 끄거나 두 번째 Company를 정상 생성하지 않았다. 불가능한 alias/잘못된 lookup projection은 unit fixture로 표시했다.
