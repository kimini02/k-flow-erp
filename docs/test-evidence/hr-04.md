## 3. 구현·SQL·Trade-off

- [EmployeeTerminationService](../../backend/src/main/java/com/kflow/erp/hr/application/EmployeeTerminationService.java): 내부 `terminateEmployee`, 입력·reason·expectedVersion 검증, standalone writable RC TransactionTemplate. Clock 1회와 Asia/Seoul d, e=d. 잘못된 manager가 참조 조회에서 새 JPA Transaction을 만들지 못하도록 **Company Port 호출 전 실제 HR 물리 Transaction을 선제 검증**한다. 유효 Root에서 Company→Employee 존재/version→상태→전체 timeline→날짜 제한의 업무 우선순위는 보존한다.
- [JpaHrAssignmentStore](../../backend/src/main/java/com/kflow/erp/hr/infrastructure/JpaHrAssignmentStore.java): 기존 Employee FOR UPDATE/국소 refresh와 최신 전체 Assignment ID 집합 재조회 재사용. HR-04 전용 실제 경계 검증은 Spring metadata+EMF holder/참여+동일 Hibernate Connection의 autoCommit/isolation/readOnly와 PG current settings를 확인한다. HR-03 Guard 호출/force 계약은 바꾸지 않는다.
- Organization ACTIVE Guard·조직 상태 잠금·IAM 호출 없음. Company 확인용 공개 조회만 사용한다. FK가 내부적으로 얻는 잠금까지 없다고 주장하지 않는다.
- 마지막 Assignment.to/updatedAt을 바꿔 flush(a+1), Employee status/end/reason/updatedAt/generation을 한 번 dirty 변경 후 flush(v+1/g+1), 최종 [joinedOn,e) 전체 coverage 확인. 신규 Assignment 없음. ID/사번/triple/from/과거 reason 보존.
- 실제 PID/XID별 PostgreSQL 로그에서 **Assignment UPDATE 1회 → Employee UPDATE 1회**, Employee UPDATE에 status/end/reason/generation/version 동시 포함을 확인. FORCE_INCREMENT 미호출, 같은 Tx DB·DTO·독립 DB version 일치. 로그 `H34-04 EVIDENCE T14/T19/A3-T07,T35`에 실제 SQL/bind와 실행 ID 보존.
- [Employee](../../backend/src/main/java/com/kflow/erp/hr/domain/Employee.java)의 generation은 private이며 직접 변경 API 없음. `Math.incrementExact`로 BIGINT 최대값에서 전체 Root 실패. Java overflow와 직접 SQL 22003을 따로 검증한다. HR-03 전보는 nonzero generation도 보존한다.
- [V6 Migration](../../backend/src/main/resources/db/migration/V6__hr_termination_and_auth_revocation_generation.sql): termination_reason VARCHAR(500), auth_revocation_generation BIGINT NOT NULL DEFAULT 0, 지정 CHECK 2개. NULL 우회·공백·control 거부, 기존 status/날짜 제약 불변. 사유 없는 기존 TERMINATED 행은 Migration을 실제로 실패시킨다. 가짜 backfill/삭제/제약 비활성화 없음.
- 기존 HR timeout 설정 재사용(Root30s / lock5s / statement30s). 부정 시험은 test-only로 lock800ms·역순 locker를 주입해 55P03/40P01을 관찰했다. 운영 timeout 성능 최적화를 했다는 뜻이 아니다.
- 종료 DTO는 마지막 flush 뒤 불변 값으로 복사하고 실제 commit 완료 후 반환. commit 실패·ACK 불명확 결과를 자동 retry/보상/원 요청 receipt로 변환하지 않는다.
- 단일 직원의 전체 timeline을 읽고 국소 refresh하는 기존 단순 구조를 유지했다. 이력 대량 처리 성능이나 페이지 간 snapshot은 검증하지 않았다. 새 Framework·테이블·외부 API는 추가하지 않았다.

## 7. 실제 개발 문제·수정 이력

1. 첫 verify는 신규 Migration 테스트의 `assertThat(PSQLException)` 오버로드 모호성으로 **testCompile 실패**했다. Throwable 타입을 명시했다. 테스트 작성 오류이며 업무 오류가 아니다.
2. 두 번째 전체 실행: Surefire53 통과, Failsafe265 중 **1 assertion 실패**. 잘못된 DataSourceTransactionManager를 주입했을 때 HR 경계 검사 전에 Company 공개 조회가 JPA Root를 열려다가 CannotCreateTransactionException으로 실패했다. 데이터 변경은 없었으나 승인된 boundary 거부 경로를 충족하지 못했다. **Production 진입 경계 문제**로 분류하고, 실제 HR 물리 Transaction 검사를 Company 조회보다 먼저 수행하도록 수정했다. 테스트 기대값을 기술 오류로 완화하지 않았다. invalid manager에서 Company 조회0/Employee lock0도 추가 확인했다.
3. 정상 최대 날짜 9999-12-31 시험을 보완하고 전체 재실행: **319 PASS**. 기존 테스트가 통과하도록 정책·검증을 삭제/무시하지 않았다.

두 실패 실행 로그는 원본 그대로 위 개발 로그에 보존한다. 테스트가 의도한 SQL CHECK/EXCLUDE 오류와 실제 테스트 실패를 구별한다.
