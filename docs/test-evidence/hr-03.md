## 3. 구현과 실제 SQL / Trade-off

코드: [EmployeeAssignmentService](../../backend/src/main/java/com/kflow/erp/hr/application/EmployeeAssignmentService.java), [JpaHrAssignmentStore](../../backend/src/main/java/com/kflow/erp/hr/infrastructure/JpaHrAssignmentStore.java), [EmployeeAssignment](../../backend/src/main/java/com/kflow/erp/hr/domain/EmployeeAssignment.java).

- 내부 `ChangeAssignment` → standalone writable READ COMMITTED TransactionTemplate. ambient Tx 거부, Root Clock 1회, Asia/Seoul d. Guard가 Company와 전체 triple을 검증한다.
- Site→Department→Position FOR SHARE 뒤 Employee를 Company+ID로 명시적 **FOR UPDATE**. JDBC는 기존 Hibernate Connection에서 실행해 query auto-flush를 피한다. 대상 Employee만 PESSIMISTIC_WRITE refresh한다.
- Employee lock 뒤 전체 Assignment ID 집합을 다시 읽고 각 대상만 refresh한다. 사전 로드 목록으로 새 tail을 누락하지 않으며 전체 clear/detach는 없다. 몇 번의 단건 refresh가 추가되는 단순 구현을 택했으며 대량 이력 성능을 측정했다고 주장하지 않는다.
- 입력/날짜/Company/Guard→존재/version→재직→전체 timeline→동일 triple→당일 제한→쓰기. 유효 미래 timeline은 지원범위 오류, 손상은 integrity 오류로 구분한다.
- 실제 Hibernate PESSIMISTIC_FORCE_INCREMENT **1회**. 수동 version 증가나 Employee dirty 필드 수정 없음. DB 같은 Tx/독립 조회와 DTO 모두 0→1, Employee의 나머지 모든 컬럼(특히 updatedAt) 불변.
- SQL 관측: `update hr_employee set version=$1 where id=$2 and version=$3`의 bind는 새 version 1/이전 0. 그 다음 기존 Assignment `effective_to/updated_at/version` UPDATE, 이후 새 Assignment INSERT. 실제 PID/XID별 trace를 실행 로그의 `H34-EVIDENCE Hibernate=...`에 보존했다.
- 기존 종료 flush가 성공한 뒤에만 신규 persist. NOT DEFERRABLE EXCLUDE 유지. old version+1/new0, old ID·triple·from·reason 불변. 전후 전체 coverage 검사, 최종 flush 후 DTO 복사, 실제 commit 후 반환. commit 뒤 재조회로 다른 요청의 version을 섞지 않는다.
- bounded 설정: `kflow.hr.assignment-command-timeout-seconds` 기본30, `kflow.hr.assignment-lock-timeout-ms` 기본5000. Root timeout 및 같은 연결의 transaction-local statement/lock timeout. 기존 Organization Guard 자체 bounded timeout 유지. 실제 Employee 대기→55P03를 시험하며 기술 오류를 업무 conflict로 바꾸지 않는다.
- 기존 exact SQLSTATE+constraint 변환 재사용. REQUIRES_NEW, 자동 retry, receipt, 보상, 전체 audit, 외부 HTTP 공개 없음.

## 7. 실제 개발 실패와 수정

- 첫 부분 실행: HrContractTest 5 PASS, 새 IT 5개 중 **1 assertion 실패**. PostgreSQL이 출력한 대문자 `FOR SHARE`를 테스트가 소문자 `for share`로 비교했다. SQL 관측 assertion의 대소문자만 바로잡았으며 잠금/순서/version assertion을 삭제하거나 production lock을 바꾸지 않았다. **테스트 관측 기대값 수정**이며 실제 업무 구현 버그로 기록하지 않는다.

- 이번 실행에서 승인된 ORM 전략이 실패해 수동 increment로 우회한 일은 없다. 실제 구현 버그를 발견했다고 꾸며 기록하지 않는다. 의도된 SQL 부정 시험의 ERROR 로그는 테스트 실패와 다르다.
